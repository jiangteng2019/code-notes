# SSO的两种主流架构范式



## 核心目标：统一认证，一次登录，多处访问

正如你所说，SSO的核心价值在于用户只需在一个地方（通常是第一次访问受保护资源时）进行一次登录认证，之后在访问其他关联系统时，无需再次输入凭证，系统能自动识别其已登录状态。

## 两种主要实现架构

### 1. 基于集中式认证中心的模式 (“平行” / 联邦身份认证)
   *   **核心思想：** 存在一个独立的、专门负责用户认证的服务（Identity Provider - IdP，如Keycloak, Okta, Azure AD, Auth0等）。各个业务系统（Service Providers - SPs）本身不直接处理用户的原始凭证（用户名/密码），它们信任IdP的认证结果。
   *   **流程简化：**
      1.  用户尝试访问受保护的业务系统A。
      2.  系统A发现用户没有本地会话，将其重定向到IdP的登录页面。
      3.  用户在IdP登录（输入凭证）。
      4.  IdP认证成功，生成一个包含用户身份信息的**令牌**（如SAML Assertion, JWT, OpenID Connect ID Token），并通过用户浏览器重定向回系统A（通常附带令牌）。
      5.  系统A接收到令牌，**向IdP验证令牌的有效性**（或根据签名/加密自行验证），并基于令牌中的信息建立本地会话。用户成功访问系统A。
      6.  用户尝试访问受保护的业务系统B。
      7.  系统B发现用户没有本地会话，将其重定向到IdP。
      8.  IdP检查用户在其域下是否已有会话（通常通过浏览器Cookie）。**如果IdP会话存在，则跳过登录界面**，直接生成一个新令牌（给系统B）并通过重定向返回系统B。
      9.  系统B验证令牌，建立本地会话。用户成功访问系统B。
   *   **关键特征：**
      *   **信任关系：** SP信任IdP。
      *   **令牌传递：** 认证信息通过令牌在IdP和SP之间传递（通常经由用户浏览器）。
      *   **本地会话：** 每个SP在用户首次访问时仍需建立自己的本地会话（基于IdP的令牌）。
      *   **标准协议：** 通常使用SAML 2.0, OpenID Connect (OIDC), CAS等标准协议实现。
   *   **优点：**
      *   **解耦清晰：** 认证逻辑与业务逻辑完全分离，职责单一。
      *   **扩展性强：** 新系统接入只需配置信任同一个IdP并实现协议即可，对现有系统影响小。非常适合集成第三方应用或不同技术栈的系统。
      *   **用户体验一致：** 所有登录界面集中在IdP，提供统一的认证体验（如MFA）。
      *   **安全性集中管理：** 密码策略、MFA、风险检测、会话超时等安全策略在IdP统一配置和强制执行。
      *   **支持身份联邦：** 更容易实现跨组织或使用社交登录（如Google, Facebook登录）。
   *   **缺点：**
      *   **实现复杂度：** 需要理解和集成标准的SSO协议（SAML/OIDC等），对每个SP有一定开发或配置工作。
      *   **依赖IdP可用性：** IdP成为关键依赖点，如果IdP宕机，所有依赖它的SP都无法进行新用户登录（已建立本地会话的用户可能不受影响）。
      *   **令牌验证开销：** SP每次验证令牌可能需要与IdP通信（或进行密码学运算），有一定性能开销（可通过本地验证/JWT优化）。
      *   **注销复杂度：** 实现全局注销（Single Logout）需要协调所有SP和IdP，协议支持度不一，实现可能复杂。
      *   **潜在重定向延迟：** 涉及多次浏览器重定向。

### 2. 基于网关/代理的统一鉴权模式 (“垂直”)
   *   **核心思想：** 所有外部请求首先到达一个**API网关**或**反向代理**。网关负责集中处理所有认证和授权逻辑。业务系统（后端微服务）本身通常不感知或很少处理认证细节，它们信任网关传递的已验证用户信息。
   *   **流程简化：**
      1.  用户请求访问任何后端服务（通过网关）。
      2.  **网关拦截请求，检查请求中的凭证**（如Cookie, JWT in Header）。
      3.  如果凭证有效且会话未过期：
          *   网关将请求**转发**给对应的后端服务，并在请求头中添加已验证的用户身份信息（如`X-User-ID`, `X-Roles`, 或传递原始JWT）。
          *   后端服务**信任网关传递的信息**，直接处理业务逻辑并返回结果。
      4.  如果凭证无效或缺失：
          *   **网关直接拦截请求，返回重定向到登录页面（由网关本身或集成的认证服务提供）。**
      5.  用户在网关提供的页面登录。
      6.  网关认证成功，为用户建立会话（如设置Cookie），并生成一个内部令牌（如JWT）用于标识用户。
      7.  网关将用户重定向回原始请求的资源，并附带凭证。
      8.  后续请求携带凭证（Cookie）到达网关，网关验证后放行并添加用户信息到后端请求。
   *   **关键特征：**
      *   **统一入口：** 网关是所有流量的唯一入口。
      *   **认证前置：** 认证和基础授权在请求到达业务服务前完成。
      *   **信任传递：** 后端服务完全信任网关传递的用户身份信息，自身通常不再进行重复认证（但可能做细粒度授权）。
      *   **会话集中：** 用户会话状态主要由网关管理（基于Cookie/JWT）。
   *   **优点：**
      *   **业务服务简化：** 后端服务几乎不需要处理认证逻辑，专注于业务，开发更简单。
      *   **安全策略集中：** 认证、基础授权、速率限制、WAF等安全措施在网关统一实施，确保一致性和强度。
      *   **性能优化：** 网关通常高效处理认证（如JWT验证），避免了每个服务重复验证。一次验证，多次放行。
      *   **易于监控审计：** 所有入口流量经过网关，便于集中日志记录和审计。
      *   **架构清晰：** 在微服务架构中，网关是标准组件，职责明确。
      *   **注销简单：** 只需在网关层面清除会话或令牌即可。
   *   **缺点：**
      *   **网关成为单点故障和瓶颈：** 网关宕机导致所有服务不可访问。高流量时网关可能成为性能瓶颈，需要精心设计和扩展。
      *   **紧耦合风险：** 业务系统与网关存在一定耦合（依赖特定Header传递用户信息）。网关配置变更可能影响所有下游服务。
      *   **潜在信任过度：** 如果后端服务完全信任网关传递的信息而不做任何校验（如JWT签名），一旦网关被攻破或配置错误，风险巨大。
      *   **灵活性受限：** 所有服务必须通过网关暴露。对于需要特定认证协议或非常规认证流程的服务，网关可能不够灵活。
      *   **网关复杂性：** 网关本身需要实现强大的认证、授权、路由、安全策略等功能，配置和维护复杂度高。

## 对比总结

| 特性                 | 基于集中认证中心 (“平行”)                  | 基于网关统一鉴权 (“垂直”)                      |
| :------------------- | :---------------------------------------- | :--------------------------------------------- |
| **核心组件**         | 独立身份提供商 (IdP)                      | API 网关 / 反向代理                            |
| **信任边界**         | SP 信任 IdP                               | 后端服务信任网关                               |
| **业务服务职责**     | 需实现协议集成，验证IdP令牌，管理本地会话 | 通常极简，信任网关传递的身份信息               |
| **认证发生点**       | IdP (用户被重定向)                        | 网关 (拦截请求并处理)                          |
| **主要协议**         | SAML, OIDC, CAS                           | 通常内部使用 (JWT + Cookie), 也可集成OIDC等    |
| **解耦程度**         | 高 (认证与业务完全分离)                   | 中 (业务服务依赖网关)                          |
| **扩展性 (新服务)**  | 高 (配置信任IdP即可)                      | 中 (需配置网关路由和策略)                      |
| **性能**             | 令牌验证有一定开销 (可优化)               | 高效 (一次验证，多次放行)                      |
| **单点故障风险**     | IdP (影响新登录)                          | 网关 (影响所有请求)                            |
| **安全策略管理**     | 集中在IdP                                 | 集中在网关                                     |
| **实现复杂度**       | SP侧需集成协议                            | 网关侧复杂度高                                 |
| **最适合场景**       | 集成异构系统、第三方应用、跨域/联邦身份   | 微服务架构内部、统一入口管控严格的环境         |
| **用户体验**         | 登录界面在IdP                             | 登录界面由网关提供或重定向                     |
| **注销 (全局)**      | 相对复杂 (SLO)                            | 相对简单 (网关清除会话)                        |

## 给你的建议

1.  **理解非常准确：** 你对SSO解决的问题和两种主要架构模式的本质（“平行”的联邦信任 vs. “垂直”的网关拦截）理解得非常到位。
2.  **模式选择取决于场景：**
    *   **选择“平行”/集中认证中心 (IdP)：**
        *   当你需要集成**多个独立的、可能是异构的（不同技术栈、不同团队维护）系统**时。
        *   当你需要支持**第三方应用接入**或**跨组织身份联邦**（如客户使用自己的账号登录你的多个系统）。
        *   当你希望**认证逻辑与业务逻辑高度解耦**。
        *   当你使用标准的身份提供商（如云厂商的IAM服务、企业AD FS）。
    *   **选择“垂直”/网关统一鉴权：**
        *   当你的架构是**清晰的微服务架构**，且所有服务**通过一个统一的API网关暴露**。
        *   当你追求**后端服务的极简化**，希望它们完全摆脱认证负担。
        *   当你需要**在入口处实施非常严格和统一的安全策略**（不只是认证，还包括授权、限流、审计等）。
        *   当你的服务主要面向**内部或受控环境**（而非大量异构第三方集成）。
3.  **混合模式是常态：** 现实中，大型系统往往采用混合模式：
    *   **网关 + IdP：** 这是非常常见的组合。网关作为统一入口，处理流量路由、基础安全策略。当网关拦截到未认证的请求时，它可以将用户重定向到后端的集中式IdP（如OIDC Provider）进行认证。认证成功后，IdP颁发令牌，网关验证该令牌并管理自己的会话（如设置Cookie），然后向后端服务传递用户信息。这结合了网关入口控制和IdP专业认证能力的优点。
    *   **网关处理基础认证，服务处理细粒度授权：** 网关验证用户身份（确保已登录），并将身份信息传递给后端服务，后端服务再根据自身业务逻辑进行更细粒度的权限检查。

## 总结

你的理解完全正确。基于集中认证中心的“平行”模式和基于网关的“垂直”模式是实现SSO的两大支柱。前者通过联邦信任和令牌交换实现解耦与灵活集成，后者通过统一入口拦截和集中认证实现业务服务简化与入口安全管控。**没有绝对的好坏，只有适合与否。** 评估你的具体需求（系统规模、架构、集成需求、团队能力、安全要求）是选择合适架构的关键。在现代云原生和微服务架构中，“网关集成集中式IdP”的混合模式通常是综合最优解。
